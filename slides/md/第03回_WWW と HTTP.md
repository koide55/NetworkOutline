# 第3回　WWW と HTTP

*ブラウザがページを表示するまでに、何が起きているのか。*

九州大学

---

<!-- _class: lead -->

## 今回の問い

> **ブラウザがページを表示するまでに、  
何が起きているのか。**

中身は、人が読める文字の「要求」と「応答」である。

この90分で、この問いに答えを出す。

---

## 到達目標

1. **URL** の各部分が何を表すかを説明できる
2. **HTTP の要求と応答** を、メソッド・ステータスコード・ヘッダの言葉で読める
3. **ステートレス** であることの利点と、その帰結を説明できる
4. **HTTP/2・HTTP/3・HTTPS・CDN** が何を改良したかを説明できる
5. **curl と開発者ツール** で、実際の通信を観察できる

---

<!-- _class: lead -->

# 3.1　WWW の仕組み

*URL で指し、HTTP で取ってくる*

---

<!-- 3.1　WWW -->

## ページが表示されるまで

1. **URL を読む** — 方式・ホスト名・パスに分ける
2. **名前を引く** — DNS でホスト名の IP アドレスを得る（第2回）
3. **つなぐ** — 443 番につなぎ、TLS で相手を確かめる（第8回）
4. **要求する** — 「GET /ja/」を送り、HTML を受け取る
5. **さらに取る** — 画像・CSS・JavaScript を次々に要求して描く

1枚のページを表示するのに、数十〜数百回の要求が送られることも珍しくない。

---

<!-- 3.1　URL -->

## URL の各部分

https://www.kyushu-u.ac.jp:443/ja/search?q=network#top

| 部分 | 例 | 意味 |
| --- | --- | --- |
| スキーム | https | どの方式で取りに行くか（HTTP を TLS で守る） |
| ホスト | www.kyushu-u.ac.jp | DNS で引く名前（第2回） |
| ポート | :443 | 省略すると https は 443、http は 80 |
| パス | /ja/search | サーバの中のどの資源か |
| クエリ | ?q=network | 追加の条件（検索語など） |
| フラグメント | #top | ページの中の位置。サーバには送られない |

---

<!-- 3.1　ブラウザ -->

## ブラウザの役割

- **要求を組み立てる** — URL から HTTP の要求を作り、サーバに送る
- **HTML を描く** — 受け取った HTML と CSS を解釈して画面にする
- **JavaScript を動かす** — ページの中のプログラムを実行し、さらに通信する（第4回）
- **覚えておく** — Cookie やキャッシュを保存し、次の要求に使う（第4回）

**ブラウザは HTTP のクライアントであり、同時にプログラムを動かす環境でもある。**

---

<!-- _class: lead -->

# 3.2　HTTP：要求と応答

*人が読める文字のやりとり*

---

<!-- 3.2　HTTP -->

## 要求と応答の形

### 要求（ブラウザ → サーバ）

```
GET /ja/ HTTP/1.1
Host: www.kyushu-u.ac.jp
User-Agent: Mozilla/5.0 ...
Accept: text/html
Accept-Language: ja

```

1行目：メソッド・パス・版。続いてヘッダ。空行の後に本文（GET では空）。

### 応答（サーバ → ブラウザ）

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 31415
Cache-Control: max-age=600

<!DOCTYPE html> ...
```

1行目：版・ステータスコード・説明。続いてヘッダ。空行の後に本文（HTML）。

**SMTP（第2回）と同じく、空行でヘッダと本文を分け、3桁の数字で結果を返す。**

---

<!-- 3.2　HTTP -->

## メソッド：何をしたいか

| メソッド | 意味 | 例 |
| --- | --- | --- |
| GET | 取得する。副作用を持たせてはならない | ページを見る、画像を取る |
| POST | 送る。サーバ側で何かが起きる | フォームの送信、LLM API への問い合わせ |
| PUT | 置き換える | ファイルを丸ごと更新する |
| DELETE | 削除する | 投稿を消す |
| HEAD | ヘッダだけ取得する | 更新されたかを確かめる |

GET に副作用を持たせると、検索エンジンのクローラがリンクをたどっただけでデータが消える、といった事故が起きる。

---

<!-- 3.2　HTTP -->

## ステータスコード：結果はどうだったか

| 1桁目 | 意味 | 主な例 |
| --- | --- | --- |
| 2xx | 成功 | 200 OK、201 Created |
| 3xx | 別の場所へ | 301 Moved Permanently、304 Not Modified |
| 4xx | クライアントの誤り | 400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、429 Too Many Requests |
| 5xx | サーバの誤り | 500 Internal Server Error、503 Service Unavailable |

> **1桁目を見れば、誰の側の問題かが分かる**

429 は「呼びすぎ」。第6回の LLM API でも出てくる。

---

<!-- 3.2　HTTP -->

## よく使うヘッダ

| ヘッダ | 意味 |
| --- | --- |
| Host | どのサイト宛てか。1台のサーバで複数のサイトを動かせる |
| Content-Type | 本文の形式（text/html、application/json、image/png など） |
| Accept / Accept-Language | 欲しい形式や言語。サーバはこれを見て返すものを選ぶ |
| Cache-Control | キャッシュしてよいか、何秒まで使い回してよいか |
| Set-Cookie / Cookie | 状態を持たせる（第4回） |
| Authorization | 認証情報。API キーなどを送る（第4・6回） |

---

<!-- 3.2　キャッシュ -->

## キャッシュと条件付きの要求

- **Cache-Control** — 「この応答は 600 秒使い回してよい」とサーバが伝える
- **条件付きの要求** — 「手元の版から変わっていれば送って」と頼む（If-None-Match など）
- **304 Not Modified** — 変わっていなければ、本文を送らずに済ませる

**DNS の TTL（第2回）と同じ考え方である。覚えておけば、何度も取りに行かなくて済む。**

---

<!-- _class: lead -->

# 3.3　HTTP の性質と進化

*ステートレスだから、分散できる*

---

<!-- 3.3　性質 -->

## HTTP はステートレスである

> **サーバは、要求と要求の間のことを覚えていない**

- 1回ごとに完結する → **どのサーバが受けてもよい**
- サーバを増やす → **負荷を分けられる**
- でもログインは？ → **Cookie で状態を持たせる（第4回）**

第6回では、LLM API も同じくステートレスであることを見る。

---

<!-- 3.3　進化 -->

## HTTP の版ごとの改良

| 版 | 年 | 主な改良 |
| --- | --- | --- |
| HTTP/1.1 | 1997 | 1本の接続を使い回す |
| HTTP/2 | 2015 | 1本の接続で複数の要求を同時に流す。ヘッダを圧縮する |
| HTTP/3 | 2022 | QUIC という新しい土台の上で動く。接続が速く、回線が切り替わっても続く |

> **版が変わっても、メソッド・ステータスコード・ヘッダの意味は同じである**

HTTP/2 以降は2進の形式で送るが、開発者ツールや curl では今日見た文字の形で表示される。  
スマートフォンが Wi-Fi から携帯の回線に切り替わっても動画が止まりにくいのは、HTTP/3 の効果である。

---

<!-- 3.3　HTTPS -->

## HTTPS が当たり前になった

- **以前** — ログイン画面など一部だけが HTTPS。他は平文で、盗み見や書き換えができた
- **いま** — ほとんどの通信が HTTPS。ブラウザは HTTP のページを「保護されていない通信」と表示する
- **後押ししたもの** — 証明書を無料で自動発行する Let's Encrypt（2015年〜）。ブラウザは HTTP/2・3 を HTTPS でしか使わない

**TLS が何を確かめているかは、第8回で扱う。**

---

<!-- 3.3　CDN -->

## CDN：距離そのものを縮める

東京と米国西海岸の往復には約 100 ミリ秒かかる。光の速さは変えられない。

> **コンテンツの複製を世界各地に置き、近い場所から配る**

- 遅延 → **近くから返す**
- 元のサーバの負荷 → **肩代わりする**
- 突発的な負荷 → **吸収する**
- 大量アクセスによる攻撃 → **和らげる**

DNS が「近い CDN のサーバ」の IP アドレスを返すことで、利用者を振り分けている（第2回）。

# 3.4　実習：HTTP を自分の目で見る

*curl・開発者ツール・小さなサーバ*

---

<!-- 3.4　実習1 -->

## 実習1：curl で要求と応答を見る

出力の例（一部。実際の値はサイトによって違う）

```
curl -v https://www.kyushu-u.ac.jp/ -o /dev/null

> GET / HTTP/2
> Host: www.kyushu-u.ac.jp
> User-Agent: curl/8.7.1
> Accept: */*
>
< HTTP/2 200
< content-type: text/html; charset=UTF-8
< cache-control: max-age=...
```

**読み方**

> で始まる行が送った要求、&lt; で始まる行が受け取った応答。

-I を付けるとヘッダだけを取る（HEAD）。

存在しないパスで 404 を、http:// で始めて 301 を見てみよう。

Windows では -o NUL とする。

---

<!-- 3.4　実習2 -->

## 実習2：開発者ツールで見る

1. **開く** — ブラウザで F12（Mac は ⌥⌘I）を押し、「ネットワーク」タブを選ぶ
2. **読み込む** — Moodle などのページを再読み込みする
3. **数える** — 要求が何本あったか、合計で何 KB 受け取ったか
4. **1本を開く** — ヘッダ、ステータスコード、プロトコル（h2・h3）を確かめる

列の見出しを右クリックして「プロトコル」を表示すると、HTTP/2（h2）や HTTP/3（h3）が使われていることが分かる。  
2回目の読み込みでは、キャッシュから取ったもの（304 や「キャッシュ」の表示）が増える。

<!-- 3.4　実習3 -->

## 実習3：小さな Web サーバを作る（bottle）

```
from bottle import route, run, template

@route('/hello/<name>')
def hello(name):
    return template('<b>Hello, {{name}}</b>!',
                    name=name)

run(host='localhost', port=8080)
```

**やること**

① pip install bottle の後、hello.py に保存して実行する。  
② ブラウザで localhost:8080/hello/kyudai を開く。  
③ curl -v localhost:8080/hello/kyudai で要求と応答を見る。  
④ URL の一部が関数の引数になることを確かめる。

webapp-security-programming-handson の基本演習2をもとにしたもの。第4回ではこれを広げて Web API を作り、  
第8回では同じ教材で脆弱性を観察する。

# 3.5　AI も HTTP を話す

*問い合わせるのも、ページを集めるのも HTTP*

---

<!-- 3.5　AI -->

## LLM API への問い合わせも、ただの POST

```
curl https://api.openai.com/v1/chat/completions \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "<モデル名>",
       "messages": [{"role": "user",
                     "content": "こんにちは"}]}'
```

**今日学んだことだけで読める**

POST メソッドで、JSON の本文を送る。

Authorization ヘッダで API キーを渡す。

答えは 200 と JSON で返る。呼びすぎれば 429。

詳しくは第6回で扱う。

---

<!-- 3.5　AI -->

## AI のクローラと robots.txt

- **クローラ** — ページを自動で集めるプログラム。検索エンジンのほか、AI の学習データ集めにも使われている
- **robots.txt** — サイトの /robots.txt に「このクローラはここを見ないで」と書く約束。2022年に標準になった
- **あくまで約束** — 守るかどうかはクローラ次第。技術的に止める仕組みではない

**例：「User-agent: GPTBot」「Disallow: /」と書くと、OpenAI のクローラにサイト全体を見ないよう求めることになる。**

---

## 演習

- **3-1**　https://www.kyushu-u.ac.jp/ja/ を開いたときに起きることを、DNS・TLS・HTTP の順に説明せよ。
- **3-2**　（手を動かす）curl -v で任意のサイトに要求を送り、ステータスコードと Content-Type を答えよ。存在しないパスではどうなるか。
- **3-3**　HTTP がステートレスであることの利点を、サーバの台数の観点から説明せよ。
- **3-4**　HTTP/2・HTTP/3 で変わったことと、変わっていないことをそれぞれ挙げよ。

---

## まとめ

| 項目 | 要点 |
| --- | --- |
| WWW | URL で資源を指し、HTTP で取ってくる。ページ1枚にも多くの要求が送られる |
| HTTP | 要求はメソッド・パス・ヘッダ、応答はステータスコード・ヘッダ・本文 |
| ステートレス | サーバは要求の間のことを覚えない。だから台数を増やして分散できる |
| 進化 | HTTP/2・3 で速くなり、HTTPS が当たり前になった。CDN が距離を縮める。意味は変わらない |
| AI と HTTP | LLM API も POST と JSON。クローラへのお願いは robots.txt に書く |
