8.1

暗号と TLS

方式は公開し、鍵だけを秘密にする

8.1　暗号

共通鍵暗号と公開鍵暗号

共通鍵暗号公開鍵暗号
鍵暗号化と復号に同じ鍵を使う公開鍵（配ってよい）と秘密鍵（本人だけ）
速さ速い共通鍵暗号の数百〜数千倍の計算が要る
代表AES、ChaCha20RSA、楕円曲線暗号
弱点鍵をどうやって安全に渡すかその公開鍵が本当に相手のものか
実際は両方を組み合わせる（ハイブリッド方式）。TLS も SSH もこの形である

ケルクホフスの原理：暗号方式が公開されていても、鍵さえ秘密なら安全でなければならない。
だから、自作の暗号は使わない。

8.1　TLS

TLS が保証する3つのこと

性質意味支える仕組み
機密性盗聴されても中身が読めない共通鍵暗号
完全性途中で書き換えられていないメッセージ認証
真正性相手が本物である証明書と署名
真正性がなければ、機密性も完全性も意味がない（偽物と暗号で話しても無駄）

いまでは Web の通信の大半が HTTPS である。証明書を無料で自動発行する Let's Encrypt の登場が、普及を後押しした。

8
8.1　耐量子暗号

量子計算機に備えた移行が始まっている

量子計算機が破るもの
Shor のアルゴリズムは RSA と楕円曲線暗号を破る。共通鍵暗号への影響は小さく、鍵を長くすれば済む
いま盗んで、後で解く
通信を保存しておき、量子計算機ができてから復号する。長く秘密にしたいデータは、今すでに危ない
組み合わせて移行する
米国 NIST が2024年に標準を定めた（ML-KEM など）。TLS では従来の鍵交換と組み合わせて使い始めている

暗号の安全性は「まだ誰も効率よく解けていない」ことの上に乗っている。前提が崩れれば、方式を入れ替える。

8.1　SSH

SSH：公開鍵でログインする

# 鍵ペアを作る（いまは ed25519 を使う）
ssh-keygen -t ed25519
#   ~/.ssh/id_ed25519      秘密鍵（渡さない）
#   ~/.ssh/id_ed25519.pub  公開鍵（サーバに置く）

# 公開鍵をサーバに登録して、ログインする
ssh-copy-id me@gw.example.jp
ssh me@gw.example.jp

# ポートフォワード（学内の Web を外から見る）
ssh -N -L 8080:intra.example.jp:80 me@gw.example.jp
パスワードを送らない
サーバは、手元の秘密鍵で署名させ、登録済みの公開鍵で確かめる。次の節のパスキーと同じ考え方である。

ポートフォワードを使うと、暗号化された SSH の中に別の通信を通せる。上の例では、手元の localhost:8080 が学内の Web サーバにつながる。

8.2　認証と認可

認証と認可は別のもの

認証（Authentication）認可（Authorization）
問いあなたは誰かあなたは何をしてよいか
例ログイン他人の成績を見てよいか、ファイルを書き換えてよいか
仕組みの例パスワード、パスキー、OpenID Connectアクセス制御、OAuth 2.0（第4回）
実際の事故の多くは認可の不備である（URL の番号を書き換えると他人のデータが見える、など）

8.2　認証

認証の3要素と、パスワードの限界

要素内容例
知識知っていることパスワード、暗証番号
所持持っているものスマートフォン、セキュリティキー
生体体の特徴指紋、顔
多要素認証は「異なる要素」を2つ以上組み合わせる

パスワードは使い回され、偽サイトに入力すれば盗まれる。サーバから漏れることもある。
SMS の確認コードも、偽サイトが聞き出して本物にすぐ入力すれば突破される。

8.3　脆弱性

代表的な脆弱性と対策

脆弱性何が起きるか対策
セッションハイジャック盗んだ Cookie で本人になりすますHTTPS、推測できないセッション ID、Cookie の属性
XSS投稿した文字列が、他人のブラウザで JavaScript として動く出力するときにエスケープする
CSRF別のサイトから、ログイン中の利用者に勝手な送信をさせる予測できないトークンをサーバで検証する
SQLインジェクション入力が SQL の一部として解釈されるプレースホルダを使う
コマンドインジェクション入力が OS のコマンドとして実行されるシェルを通さず、引数を分けて渡す

XSS はクロスサイトスクリプティング、CSRF はクロスサイトリクエストフォージェリの略。
この後の実習で、これらを手元の PC で実際に起こして観察する。

17
8.3　共通の構造

根は「データとコードの境界のあいまいさ」

データのつもりの入力が、命令として解釈されてしまう
  • SQLインジェクション SQL として解釈される
  • XSS JavaScript として実行される
  • コマンドインジェクション シェルのコマンドとして実行される

共通の対策は「データをデータとして扱う」こと。文字列を連結して命令を組み立てない。

18
8.3　SQLインジェクション

文字列の連結と、プレースホルダ

危険：入力が SQL の一部になる
sql = (f"SELECT * FROM users "
       f"WHERE name='{name}' AND pw='{pw}'")

# pw に  ' or 'a'='a  を入れると
# WHERE name='koide' AND pw='' or 'a'='a'
# → 常に真。パスワードなしで通る
安全：値は別に渡す
cur.execute(
    "SELECT * FROM users "
    "WHERE name = ? AND pw = ?",
    (name, pw))

# 入力は SQL ではなく「値」として扱われる

実際のアプリでは、パスワードは平文で保存せず、ハッシュ値にして保存する（教材の発展演習）。

8.3　Cookie

Cookie を守る属性と工夫

属性・工夫効果防ぐもの
HttpOnlyJavaScript から読めなくするXSS による Cookie の盗み出し
SecureHTTPS のときだけ送る盗聴による漏えい
SameSite別のサイトから始まった要求には付けない（Lax・Strict）CSRF
署名値が書き換えられたことを見抜くCookie の改ざん
HttpOnly を付けても XSS そのものは防げない。根本の対策は出力のエスケープである

8.4　AI

プロンプトインジェクション：メール1通で起こりうる

2025年には、細工したメールを1通送るだけで、業務用の AI アシスタントに社内の情報を外へ送らせうる脆弱性が報告された（提供元が修正済み）。

24
8.4　AI

プロンプトインジェクションは、8.3 と同じ構造

データとコードの境界のあいまいさ —— その最も新しい現れ
  • SQLインジェクション データが SQL として解釈される
  • XSS データが JavaScript として実行される
  • プロンプトインジェクション データが指示として解釈される

ただし SQL にはプレースホルダという確実な対策があるが、自然言語には「ここからはデータ」と示す確実な仕組みがない。
だから根本的な解決は難しく、対策は「被害を限る」方向になる。

25
8.4　AI

対策は、破られても被害を限ること

最小権限
必要な道具と権限だけを与える。送信できる相手を限る
承認点
送信・削除・支払いなど、取り消せない操作の前に人間が確認する（第7回の実習）
信頼できない入力の隔離
外から来た文書を、指示として扱わない設計にする
記録と監査
AI が何を読み、何をしたかを、後から追えるようにする
サンドボックス
影響が外に出ない環境で動かす（第5回のコンテナ）

狙うのは「破られない」ことではなく「破られても被害が限られる」こと。人間の新人に対する扱いと同じである。

8.4　信頼境界

AI の使い方によって、信頼境界の位置が変わる

使い方新たにできる信頼境界主な脅威最初に効く対策
P1 チャットで使う利用者 ⇄ AI の提供者機密情報の入力、学習への利用契約と設定の確認、利用ログ
P2 アプリに組み込むシステムプロンプト ⇄ 利用者の入力直接のインジェクション、出力をそのまま使う入出力の検査、出力の形の固定
P3 RAG取り込む文書 ⇄ モデル間接のインジェクション、知識の汚染取り込み元の管理、検索時の権限
P4 ツールを実行させるモデルの出力 ⇄ 実行する仕組み道具の誤用、権限の与えすぎ道具ごとの権限、承認点、監査ログ
P5 複数のエージェントエージェント ⇄ エージェント記憶や通信の汚染、偽のエージェントエージェントの識別、通信の検証

段は積み上がる。上の段は下の段の脅威をすべて引き継ぐ。
出典：JNSA 調査研究部会 AIセキュリティWG「AIシステムを守る第一歩 ― 脅威モデリング3手法を比較する」（2026）をもとに作成

8.4　脅威モデリング

脅威モデリング：作る前に、攻撃を先に考える

1
DFD を描く
データの流れを図にし、信頼境界を見つける
2
優先度を付ける
どの境界から調べるかを決める
3
脅威を挙げる
境界ごとに STRIDE（なりすまし・改ざん・否認・情報漏えい・サービス妨害・権限昇格）で洗い出す
4
リスクを評価する
起こりやすさと影響の大きさで重みを付ける
5
対策を決める
ビジネスへの影響を考え、手を打つ順番を決める

題材（レポート課題）：外部の文字起こし API と LLM API を使う「AI議事録アプリ」（P2 に当たる）。
録音・文字起こし・要約という機密性の高いデータが、どの境界を越えるかに注目する。

8.5　まとめ

8回を通じて、繰り返し現れた考え方

階層化
下の層を土管として扱えるから、アプリケーションだけを考えられる
名前と対応表
ドメイン名と IP アドレス、URL とリソース。名前を引くところが要であり、弱点でもある
状態の置き場所
HTTP も LLM API も状態を持たない。Cookie や履歴の送り直しで「続き」を作る
HTTP と JSON の上に積む
REST、Web API、LLM API、MCP。新しい仕組みも同じ土台の上にできている
データとコードの境界
SQLインジェクション、XSS、プロンプトインジェクション。同じ構造が形を変えて現れる
信頼の置き場所
証明書、パスキー、OAuth、承認点。誰を、何によって信じるかを設計する

新しいサービスに出会ったら、どの名前を引き、何を HTTP で運び、状態をどこに置き、誰を信頼しているかを見抜いてほしい。

まとめ

  • 暗号と TLS公開鍵の仕組みで相手を確かめて鍵を共有し、データは共通鍵で流す。証明書の警告は無視しない
  • 認証と認可あなたは誰か、と、何をしてよいか。パスキーは、利用者が騙されても端末が騙されない
  • Web の脆弱性Cookie は持っている人を本人とみなす。XSS や SQLi は、データが命令として解釈される問題
  • AI のセキュリティプロンプトインジェクションは同じ構造の最新の現れ。対策は最小権限・承認点・記録
  • 信頼境界AI の使い方で境界の位置が変わる。作る前に脅威モデリングを行う
  • 全8回アプリケーション層は変わり続けるが、名前・HTTP・状態・信頼という骨組みは変わらない
